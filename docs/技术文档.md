## 1. 架构总览

```
┌──────────────────────────────────────────────────────────────┐
│ pywebview 6.2 (WebView2 / EdgeChromium) 原生窗口              │
│   web/index.html + app.js + style.css  —— 单页应用，800ms 轮询 │
│   window.pywebview.api —— Bridge：选文件夹 / 选文件 / 另存为   │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTP 127.0.0.1:8765（+0..19 端口回退）
┌───────────────────────────▼──────────────────────────────────┐
│ core/api.py · App（业务编排层）                                │
│   ThreadingHTTPServer + make_handler() 路由，GET / POST /      │
│   PUT / DELETE；长任务用后台线程 + 状态字典 + 取消标志         │
└───────┬──────────────┬──────────────┬──────────────┬─────────┘
        │              │              │              │
   core/db.py    core/player.py  core/fetchsong.py  core/organize.py
   SQLite 单连接  mpv JSON IPC     七源引擎 + B站    计划/执行/撤销
        │              │              │              │
   library.py    lyrics.py      playlist_file.py   playlist_export.py
   导入扫描       歌词四源        清单解析           清单导出
        │                             │
   trash.py（Windows 回收站）   music-dl.exe（外部进程，本地 HTTP）
```

**关键设计决策**

| 决策 | 原因 |
| --- | --- |
| 前端与后端用本地 HTTP 而非 pywebview JS API 全包 | 便于 `--browser` 调试、curl 冒烟、UI 自动化脚本复用同一套接口 |
| SQLite **单连接 + RLock**（`check_same_thread=False`） | 早期每线程一个连接，800ms 轮询会泄漏成千上万个连接；单连接串行化避免 `SQLITE_BUSY` |
| 曲库 = 「一首歌一份文件 + `playlist_songs` 引用」 | 多歌单共享同一实体文件，歌单整理才能只搬位置、不改归属、不复制音频 |
| 长任务后台线程 + 状态轮询 | 避免 HTTP 请求超时；前端可显示进度、取消、逐首结果 |
| 所有删除走 Windows 回收站 | 替换/整理/删除均可人工找回，避免不可逆数据丢失 |
| 名称与版本只在 `core/meta.py` 定义 | 窗口标题、网页标题、品牌区、bootstrap、spec、文档统一来源 |

## 3. 启动与运行

1. `main.py` 计算 `BASE`（源码目录 / exe 目录）与 `RES`（`_MEIPASS` / 源码目录）。
2. `DB(default_db_path())` 建库 → `MpvPlayer()` 启动 mpv 并连 IPC → `App(...)` 初始化各任务状态。
3. `start_server(app, host="127.0.0.1", port=8765, tries=20)`：端口被占则顺延，最多 20 次。
4. pywebview 创建窗口，加载本地 HTTP 首页；`Bridge` 暴露 `choose_folder`、`choose_file`、保存对话框等原生能力。
5. 前端 `GET /api/bootstrap` 拿全量初始状态（含 `app` 名称/版本、`organize` 状态、`default_root`），随后 800ms 轮询各任务状态。

**调试**：`python main.py --browser --port 8899` 用默认浏览器打开，可直接用 curl 打接口。

**打包**：onedir。`音乐播放器.spec` 的 `datas` 打包 `web/`、`vendor/mpv/`、`music-dl.exe`；
`hiddenimports=['webview.platforms.edgechromium','clr']`；`name='苍龙音乐管理播放器'`。
交付目录内 exe 与 `_internal\` 必须同在。

## 4. 数据库

单文件 `data\library.db`，六张表：

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `songs` | `id, title, artist, album, duration, file_path UNIQUE, file_size, file_hash, bitrate, format, source, status, added_at, missing` | 一行 = 磁盘一份真实文件；`source` 存来源快照 JSON 字符串；`missing` 独立标记，**不能复用 `status`**（否则缺文件的歌会从列表消失，再没机会补回） |
| `playlists` | `id, name UNIQUE, sort_order, created_at, kind` | `kind='recycle'` 为回收站；排序决定侧栏顺序，也是歌单整理的分组优先级 |
| `playlist_songs` | `playlist_id, song_id, position, added_at` | 引用表，复合主键；`ON DELETE CASCADE` |
| `settings` | `key, value` | `library_root` / `main_view` / `volume` / 播放模式等 |
| `dl_memory` | `song_key, source, card_id, name, verdict('pick'/'reject'), hits` | 下载记忆按「归一化歌名\|归一化歌手」存，跟歌不跟 id |
| `lyrics` | `song_id, source, lrc, status, fetched_at` | `notfound` 也留行，用于 6 小时冷却 |

`REAL_MEMBERS` 常量定义「还属于某个正常列表」的歌 id 集合，删除、统计、全部歌曲视图都以此为准
（回收站不算）。排序 SQL 用白名单 `_ORDER` 映射，不拼接原始字符串。

**`move_paths(pairs)`（0.3.0）**：因为 `file_path` 上有 `UNIQUE COLLATE NOCASE`，
批量互换/搬移路径会撞唯一约束。实现为**单事务两阶段**：先把所有旧路径改成占位值，
再统一写最终路径；只改路径，不动元数据。整理完成后一次性调用。

## 6. 下载与评分子系统（`core/fetchsong.py`）

### 6.1 数据源

- **七源**：`kugou / qq / netease / kuwo / migu / qianqian / soda`，由 `music-dl.exe` 提供；
  `Engine` 把它当本地子进程，随机空闲端口起 HTTP 服务，封装 `search / search_many / download`。
- **B 站**：**自研直连，独立模块 `core/sources/bilibili.py`**（2026-11-09 升级为交付版 2610 行，
  见 [整合报告](B站模块整合报告-2026-11-09.md)）。对外仍是 `bili_raw` / `bili_search` /
  `bili_cards` / `bili_download_audio` / `bili_fallback` 四个契约 + 别名，`fetchsong.py`
  按名导入 21 个符号。取 DASH 纯音频流拼 m4a，不经过引擎；412 指数退避 + 换 UA/cookie、
  90 秒总预算、按命中翻页、下载写回歌名/歌手/封面标签（`.tagbak` 失败回滚）、
  标题/标签/简介三字段投票；`bili_up_search` / `bili_up_resolve` 已于 2026-11-09 接进宿主，
  见 6.1.1。score 恒 ∈[0,1]（headroom 加分 + `_clamp_score` 夹底），音轨读超时 25s，
  超时清理半截 `.part`。

### 6.1.1 按 UP 主搜 B 站（独立入口，2026-11-09）

入口是顶栏 `#btnUp`（触屏由 `phone.js` 自动搬进 ⋮ 菜单），面板 `#upModal` 与状态 `S.up`
**完全独立**于在线搜歌面板，避免与「重搜替换」的 `S.sr.replace` 语义纠缠。
`phone.js` 的 `FS_IDS` / `CLOSE_BTN` 必须登记 `upModal`，否则手机端不会变全屏子页、
返回键也关不掉；触屏点菜单按钮后 120ms 自动收菜单，所以面板延后 160ms 再弹。

后端三个 GET（两端 `api.py` 各做手术式插入，绝不整文件覆盖）：

| 端点 | 作用 |
| --- | --- |
| `/api/up/resolve?q=` | UP 名 / mid / 空间链接 → `{up, candidates}`；解析失败仍尽量给前 5 个候选 |
| `/api/up/candidates?q=` | 单独列候选，供「周杰伦解析到粉丝号」时手动点选 |
| `/api/up/search?q=&mid=&page=&limit=` | 作品列表 → 一卡一组，按 `pubdate` 倒序，最多 3 页 90 条 |

关键契约：模块新增 `bili_up_cards(rows)` 把 27 键行转成 `bili_cards` 同构卡片；
**不走 `group_results`**（它会给 B 站组 +2.0 按相关度重排），UP 列表的 `score` 固定 1.0
只表示「是该 UP 的作品」；`tag/tname/favorites` 是列表接口缺省值，不是解析失败。
下载仍复用 `POST /api/search/grab`，不新增下载端点。

`start_grab()` 增加 `bili_only` 判定：当所有卡片都是 B 站源时放宽 `fetch_available()`
前置检查，`_grab_worker()` 的 `engine.start()` 失败也只降级成一个带空 `work_dir` 的轻量句柄
（`_bili_stage` / `recover_leftover` 只用这个属性）。理由是真机 Go 引擎取流全失败而 B 站直连可用；
混合引擎源时原检查规则不变。UP 接口是频率级风控，宿主用类级 `_up_lock` 串行化，
模块内另有 1.2s 限速、10min 名字缓存与 2min 列表缓存，外层禁止并发调用。

**2026-11-10 补**：UP 面板的目标列表下拉补上 change 监听（`upPl` → `onPlaylistPick()`），
选「＋ 新建列表…」才会弹输入框；`upStartPoll()` 完成分支补 `refreshPlaylists()`，
下载一结束就更新侧栏计数与「全部歌曲」总数（原来只有 `reloadView()`，计数会一直停在
打开页面那一刻）。全局 `poll()` 另加 30 秒一次的低频计数刷新，覆盖后台 foldersync
只改数据库、不推前端的情况；不会每 800ms 拉一次 bootstrap。

### 6.2 源冷却（0.2.5 修复）

`Engine._kills / _scope / _scoped` 维护按源的冷却表：
失败**按歌去重**、连续 3 首不同的歌都挂才冷却、冷却 2/4/8 分钟指数退避、成功一次复位；
活着的源不足三家时冷却源仍参与**搜索**（只搜不下），全源失败后再兜底捞回。
此前的「一首歌两次 502 就冷却 10 分钟」曾导致 44 首集体失败。

### 6.3 匹配与评分

- `norm()` 归一化：剥前缀、认括号别名、折叠变音符与西里尔字母。
- `version_tags() / bad_version() / ver_text()`：语义词表 + 正则识别
  现场/演唱会/翻唱/DJ/伴奏等，`is_studio_cut()` 做时长与版本双重否决；
  **专辑名里的坏词只降 0.15 分，不判死**（0.2.6 修《总有美好在路上》）。
- `score(card, title, artist, duration)`：歌名相似度 + 歌手命中度 + 时长 + 音质档 + 高清加分；
  候选歌手为空时 `"" in t` 曾恒真白送 0.28 分，已修。
- `rank_cards(cards, title, artist, duration, limit=2, min_score=0.55, bili_bonus=0.0)`；
  `fetch_best(engine, ..., bili_bonus=0.0)`；`_wide_retry()` 做全源宽松兜底。
- 严格集时长门槛 **±15s**（0.2.5 从 ±10s 放宽）；库内时长不可信时二段式宽搜，
  落库时长改用**平台元数据**，实测只兜底（0.2.6 修「错时长污染导致永远补不上」）。
- 歌手串超过两人只留第一人，搜不到再用纯歌名补一枪。

### 6.4 候选竞速与「B站优先」

`_buy_best()` 逐候选下载并实测码率，留最好那份；有无损或 ≥280kbps 不再额外兜底。
`_bili_try_better()` 在平台版本之上比一次 B 站音轨，兼容 dict / tuple 两种 `exclude`。
0.2.9 后：勾「B站优先」时 B 站候选排到下载队列最前，下成且音质过得去就定稿，
不回头逐条试平台候选；进度文案改「正在比较候选 x/y」；完成提示用 **`info["source"]` 实际来源**。

### 6.5 联网重下（`api._redownload_one()`）

共用单曲 / 批量 / 歌单三条路径：仅用**歌名 + 歌手**、`duration=0`、
`rank_cards(min_score=0.60, limit=3)`；与 `src_info.score` 或下载记忆里 pick 卡片**实算的基准分**比较，
**更高分才替换**，旧文件进系统回收站。单首任何异常只记该首失败，不炸整批。
`rejects` 同时兼容 `db.dl_rejects()` 返回的字典列表（0.2.8 曾因按二元组解包 ValueError 炸批）。

## 7. 歌单导出（`core/playlist_export.py`）

`normalize_fmt()` → `build(songs, name, fmt)` → `write_file()`。
`_missing(song)` 同时信 `missing` 标记**和磁盘实查**（0.2.9 修「只信标记导致状态过时」）。
TXT 与 `playlist_file.py` 解析器互通、CSV 带 UTF-8 BOM、M3U8 写绝对路径。
回收站歌曲不进入导出集合。

## 8. 歌单整理（`core/organize.py`）

- `safe_dir_name() / unique_dir_names()`：去 Windows 非法字符、避开扫描器跳过的名字、重名去重。
- `build_plan(db, master, root)`：**纯计算**，返回分组、目标路径、跨盘字节、剩余空间、跳过数。
  主单优先，其余按侧栏顺序取第一个所属歌单；主单为「全部歌曲」则平铺根目录。
- `move_one(src, dst, copy_mode)`：同盘原子移动；跨盘 `copy2` + 大小/指纹校验 + 原件进回收站；
  `_unique_dst()` 保证同名加 `(2)`、**绝不覆盖**。
- `execute()`：单首异常隔离、`progress` 回调、可中断、完成后 `db.move_paths()` 批量改库路径。
- 撤销与崩溃恢复：`_write_log()` 写 `data\organize\last.json`（带重试避开 Windows `os.replace` 竞态）、
  `log_state()` 按 mtime 缓存、`resume_pending()` 启动时补写、`undo_last()` 还原文件与路径。
- 日志写入失败**不打断整理**（0.3.0 修：界面轮询读日志时的 `PermissionError` 曾被误判成搬歌失败）。

## 14. 目录即歌单 v3（桌面 0.6.0，2026-11-08）

> 方案演进：`方案-目录歌单与整理.md`(v1) → `方案v2-文件为准的目录歌单与同步.md`
> → `方案v2.1-决策落地检查.md` → **`方案v3-目录即歌单.md`（以这版为准）**。
> 前几版的 `folder_rel`、虚拟歌单、主单重排、`trash_items` 批次表、排序锁全部砍掉。

### 一条规则

**用户指定的根目录下，目录树 = 歌单树（1:1，树形侧栏）；一首歌只属于它直接所在目录的那个歌单。**
文件是真相，库是投影。非音频文件不入库、不显示。对歌单的操作就是对磁盘上对应文件/目录的操作。

### 首次启用

顶栏「设置根目录」→ 选根目录 → 预览显示「N 个目录 / M 首音频 / 将新建 K 个歌单」→ 确认。
换根时三选：**移出曲库（文件留原地） / 一并搬进新根 / 取消**。
旧的平铺歌单退役（只删列表、不动文件）；不在新根下的历史记录清掉（也只清库）。
未启用目录模式时，程序保持 0.5.1 的旧行为，老库完全不受影响。

### 新增模块

| 文件 | 职责 |
|---|---|
| `core/foldersync.py` | 目录树扫描、歌单树对账、移动 vs 删除识别、熔断、增量缓存 |
| `core/recycle.py` | 程序内删除 → `<根>/_回收/<批次>/<原相对路径>/`；按批次列举 / 还原 / 送系统回收站 |
| `core/db.py` | `playlists` 加 `parent_id`、`folder_path`；目录歌单的建/删/改名/排序/唯一归属方法 |

**回收零状态**：不建表、不留标记。回退路径 = 根 + 去掉 `_回收\<批次>\` 前缀。
删歌 = 直接删库记录；还原 = 文件搬回原处 → 下一次对账自动重新入库并归到对应歌单。
单曲删除只搬音频（同名 .lrc / 封面留原地）；整目录删除连非音频一起搬、一起回来。

### 操作映射

| 动作 | 磁盘 | 库 |
|---|---|---|
| 新建子歌单 | `mkdir` | 建 folder 歌单行 |
| 重命名歌单 | 重命名目录 | `rebase_folder_paths` 批量改子树路径 |
| 删除歌单 | 整目录搬进回收批次 | 删歌单树 + 歌曲记录 |
| 加歌到另一歌单 | 移动文件 | 改 `file_path` + 唯一归属 |
| 从歌单移除 / 删歌 | 音频搬进回收批次 | 删记录 |
| 上移 / 下移歌单 | 无 | 同级 `sort_order` 交换 |
| OS 里新建/改名/删文件 | 用户自己做 | 对账发现后跟着变 |

点父歌单**只显示本级**，徽标 `本级 / 含子孙合计`，避免一首歌出现在两个歌单里。
歌单内歌曲顺序 = 文件名自然排序（01/02/10），不支持拖拽调序。

### 安全约束（都是必须项）

1. `_回收` 整棵跳过扫描、不建歌单、不入库
2. 原路径消失 → 先按 `file_hash` 在「新出现的文件」里找 → 找到=搬家（改归属），没有=真删
3. 根不可读 → **整轮跳过**，不清库；一次性消失 > 20% 且 > 10 首 → 挂起整轮，前端弹确认
4. `playlists.name` 有 UNIQUE，同名目录显示名按「末级名 → 父/名 → 全相对路径 → (2)」消歧；
   真正身份是 `folder_path`
5. 增量：`mtime + size` 没变跳过读标签/算指纹（缓存在 `data/foldersync_cache.json`）
6. 同步触发：启动 4 秒 / 每 10 分钟 / 手动「立即同步」/ 还原后；程序自身操作即时生效
7. 下载落盘：新歌落到目标歌单目录，补歌/重下落回歌曲原目录，避免同步把歌归错

### API

```
GET  /api/folders/status          POST /api/folders/preview|root|sync|create|order|move|delete-songs
GET  /api/recycle/batches         POST /api/recycle/restore
POST /api/recycle/purge          （带 batch = 新回收目录；不带 = 旧回收站兼容路径）
```
原有 `/api/playlists` 系列在目录模式下自动映射到文件操作，前端调用方式不变。
bootstrap 增加 `folders` 字段（`mode / root / 同步状态`）。

### 14.3 回收批次自动清理 + 自然排序崩溃复盘（0.6.2 / 0.7.3）

**自动清理（第 14 项待办）**：`_回收/<批次>/` 不再只增不减。

- 触发：每轮目录对账成功后 `foldersync.maybe_auto_purge()`，用 setting
  `recycle_last_purge` 节流到 **6 小时**一次；目录模式没开时完全不跑。
- 规则：空批次（还原/清空后剩下的目录壳）立即清；其余按批次时间倒序，
  **最近 10 批保底**，超过 `recycle_keep_days`（默认 **30 天**）的整批才清。
  批次时间以目录名 `YYYYMMDD-HHMMSS` 为准——目录 mtime 会被还原/清空刷新，不能当依据。
- 清理走 `recycle.purge()` → `trash.delete_files()`：Windows 送**系统回收站**（仍可找回）；
  安卓 `trash_android` 是**永久删除**，前端面板与确认文案已如实写明。
- 配置与展示：settings `recycle_auto_purge` / `recycle_keep_days`；
  `POST /api/folders/purge-config`（保存后立即按新规则跑一次）；
  `/api/folders/status` 与 `bootstrap.folders` 增加 `purge` 字段；
  回收面板顶部是开关 + 天数 + 上次清理结果，状态条在 5 分钟内追加提示。
- **踩坑**：`keep_days or 30`、`keep_batches or 10` 会把显式传 0 当成没传，
  保底关不掉 → 改成 `is None` 判断，单测覆盖。

**真机才暴露的崩溃**：`POST /api/folders/preview` 扫真机
`/storage/emulated/0/1_Music`（35 目录 / 1888 音频）返回
`扫描失败：'<' not supported between instances of 'int' and 'str'`。

- 根因：`foldersync.natural()` 直接返回 `[int(t) if t.isdigit() else t.lower(), ...]`，
  Python3 比较两个这样的 list 时，「1.mp3」的数字段会撞上「a.mp3」的文字段 →
  `int < str` 抛 TypeError。之前三档 QA / TestMuMu / 桌面 198 首库的文件名
  恰好没有「数字开头与文字开头混排」，所以一直没复现。
- 修法：两段都包成 `(类型标记, 值)` —— 数字 `(0,int)`、文字 `(1,str)`，
  比较时先比标记，不同类型永不直接互比。`db.DB.natural_key()` 同步改
  （否则点开目录歌单里的歌曲列表也会崩）。
- 回归：`tools/qa_autopurge.py::t_natural_sort` 覆盖
  `1.mp3 / a.mp3 / 10.mp3 / 01.wav / A.flac / 中文.m4a` 混合排序。
  **规律：造测试数据必须包含数字开头 + 文字开头的文件名。**

**最终验证（0.6.2 / 0.7.3）**

- 桌面：在**真实 198 首曲库**上先备份 `data/library.db`，实切目录模式

### 14.4 目录模式转默认 + 查重复归集（0.6.3 / 0.7.4，2026-11-08）

按拍板收敛长期双轨：目录模式成为默认，P2 里的查重落地，
「缺失补下载清单」因与 v3「文件是真相」冲突而取消。

#### 转默认：三态 setting + 存量库一次性确认

`folder_mode` 从「默认关闭」改成三态：

| setting | 含义 | `folder_mode()` |
| --- | --- | --- |
| `'1'` | 已启用 | True |
| `'0'` | 用户选择暂时保留旧歌单 | False |
| `''` | 尚未表态（老库升级） | 无普通歌单 → 自动写 `'1'` 并 True；有普通歌单 → False |

关键是**绝不在升级时静默 `drop_normal_playlists()`**：真机有 1913 首歌和
「我喜欢」148 首，桌面也有 198 首 + 5 个旧歌单。`folders_state()` 下发
`migration:{needed,playlists,songs}`，前端 `mgModal` 弹一次性确认；
用户点「转为目录模式」才走 `POST /api/folders/migrate {choice:'convert'}`
（清列表、文件不动、按现有 `library_root` 起一轮对账），
点「暂时保留」则落 `'0'`，以后仍可用「设置根目录」切换。

**新增 `folder_root_set` 标记的必要性**：新装默认开目录模式后，
`library_root` 只是扫描默认路径（桌面 `D:\Music2`、安卓 `/storage/emulated/0/Music`），
此时用户选它的**子目录**会被 `folders_preview` 当成「换根」、误弹换根三选，
`folders_set_root` 的「新旧根不能互相包含」也会误拦。0.6.1 修过一次（靠
`folder_mode()` 为假），转默认后又回来了。现在只有**显式设过根**
（`folder_root_set='1'`）才启用这两条换根保护。

**边界加固（真机 QA 复盘）**：最初把「没有普通歌单」等同于「新装」，
但老库也可能是「歌单早已是 folder 树、setting 却没落过，曲库仍有一千多首歌」。
这种库若被自动写 `'1'`，启动 4 秒后的 `auto_loop` 会立刻按默认根跑一轮对账，
可能把根外的历史记录清掉。现改为**只有 `normal_playlist_count()==0` 且
`songs==0` 的真正空库**才自动启用；任何有歌但未表态的库一律维持关闭并弹确认。
`folder_migration()` 的 `needed` 同步改为「有普通歌单 **或** 有歌」，
且 setting 已是 `'0'`/`'1'` 时不再重复弹窗。
三态单元验证覆盖 5 种组合（含真机那种 `normal=0 / songs=1887`）。

#### 查重：`core/dedup.py`

- 判重口径：复用入库时的 `file_hash`（`library.fingerprint()` =
  size + 首尾各 512KB 的 sha1），**不重新扫全盘**；空 hash 跳过并在预览报 `skipped`。
  `_回收` 整棵排除。
- 保留规则：`(相对路径层数, natural(rel), rel.lower())`，即层级最浅、
  同级自然序最前。注意 `natural()` 已在 14.3 改成 `(0,int)/(1,str)` 元组，
  混合文件名不会抛类型错误。
- 归集：`recycle.move_to_recycle(root, paths, tag="查重")` →
  `<根>/_回收/<YYYYMMDD-HHMMSS-查重>/<原相对路径>/`。批次名只加后缀，
  前 15 字符仍是时间戳，`auto_purge` 的 `^(\d{8})-(\d{6})` 解析照常工作；
  与删歌共用 `list_batches` / `restore`，不新建「重复歌+日期」目录，
  也不改歌单结构。
- 只搬文件、不动数据库，随后 `foldersync.start(reason='dedup')` 由
  「文件是真相」的统一逻辑清掉消失的记录，避免两套删除路径。
- API：`POST /api/folders/dedup/preview`（只读）/ `/api/folders/dedup/apply`
  body `{hashes:[...]}`（可只归集选中的组）。前端 `ddModal` 先预览分组、
  勾选、**二次点击**确认（项目里不用原生 `confirm`，WebView 行为不可靠）。
